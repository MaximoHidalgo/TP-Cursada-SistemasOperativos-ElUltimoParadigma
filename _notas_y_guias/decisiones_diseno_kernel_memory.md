# Decisiones de Diseño: Kernel Memory

## Refactorizaciones y Clean Code (Hardening)

- **Refactorización de Kernel Memory (Clean Architecture)**: Siguiendo los principios de Clean Code y las reglas de `refactor-c-modules`, se refactorizó el módulo `kernel_memory` para:
  1. Mantener `main.c` estrictamente como un *entrypoint* orquestador (extrayendo el bucle de escucha de sockets).
  2. Abstraer la deserialización segura utilizando la estructura `t_buffer_reader` en reemplazo de operaciones manuales y riesgosas de `memcpy` con aritmética de punteros.
  3. Desacoplar rutinas monolíticas, como `iniciar_contexto`, aislando las responsabilidades de inicialización de *logger* y configuración en `inicializar_entorno`.
  4. Delegar todo el código acoplado dentro de las sentencias del `switch` de red en *handlers* puros de única responsabilidad.

## Memoria de Instrucciones y Contextos

El diseño de la gestión de programas y contextos de ejecución fue implementado respetando los lineamientos estructurales:

- **Almacenamiento Per-PID (Estructuras Nativas)**: Se definió la estructura global `t_programa` que encapsula la matriz de instrucciones en texto (`char** instrucciones`) y el contexto de ejecución del proceso.
- **Contexto de Ejecución Fiel**: La estructura `t_contexto_ejecucion` empaqueta, según solicita la consigna, la representación de `t_registros` (PC, AX, BX, EAX, etc.) y la `tabla_segmentos` (implementada como una `t_list*` de elementos `t_segmento`).
- **Control de Actualizaciones Desacoplado**: En el handler de actualización de contexto (`procesar_actualizacion_contexto_handler`), se actualizan *únicamente* los registros del contexto guardado. Se ignora intencionalmente sobreescribir la tabla de segmentos con la enviada por la CPU para mantener a Kernel Memory como única y absoluta "Single Source of Truth" (fuente de verdad) sobre los mapeos de la memoria. Esto previene condiciones de carrera o *downgrades* no deseados en la paginación/segmentación.
- **Sincronización (Thread-Safety)**: Se utiliza `pthread_mutex_lock(&ctx->mutex_programas)` tanto al recuperar instrucciones (para el Fetch) como al buscar/actualizar contextos, asegurando consistencia ante un escenario de concurrencia de múltiples CPUs consultando simultáneamente.

## Archivos de Pseudocódigo (Instrucciones)

El manejo y almacenamiento de los scripts de pseudocódigo fue diseñado buscando optimización de recursos y velocidad de respuesta:

- **Asociación Estructural Per-PID**: Tal como se exige, se implementó una estructura central `t_programa` que, a través de su atributo `pid`, vincula permanentemente al proceso con la matriz completa de sus instrucciones (`char** instrucciones`).
- **Lectura Temprana y Cierre (Fail-Fast & Eager Loading)**: En la función `crear_proceso`, el archivo de pseudocódigo (texto separado por `\n`) se abre, se lee línea por línea (usando `leer_lineas` con limpieza mediante `string_trim`), y **se cierra de inmediato**. No se mantienen descriptores de archivo (`FILE*`) colgados (abiertos) durante todo el ciclo de vida del proceso, ahorrando recursos críticos del SO e impidiendo el bloqueo del archivo.
- **Eficiencia en el Fetching de CPU**: Al recibir la solicitud de la CPU, la función `obtener_instruccion` accede directamente al array en memoria mediante el índice `PC` (`prog->instrucciones[pc]`). Esto convierte el acceso en una operación $O(1)$ sin realizar I/O de disco, logrando una transferencia a la CPU sumamente veloz y segura tras el *instruction delay*.
- **Mecanismo de Seguridad Fallback**: Se incluyó una ruta *fallback* (`../utils/scripts/`) al abrir los archivos. Esto permite flexibilidad y resiliencia en los entornos de prueba automatizados en caso de que el path provisto desde el Kernel sea puramente relativo a otra carpeta.

## Memoria de Usuario o Datos (Memory Sticks)

El diseño del esquema de memoria y el almacenamiento de datos mediante *Memory Sticks* se estructuró con un alto grado de cohesión y Clean Code:

- **Esquema de Segmentación Pura**: El módulo Kernel Memory implementa fielmente un esquema de segmentación donde cada proceso (identificado por PID) tiene su propia tabla de segmentos (`t_list* tabla_segmentos` dentro de su contexto). A nivel global, los huecos libres y segmentos ocupados son gestionados de forma concurrente, resguardados por su mutex de memoria. La estructura `t_segmento` (`utils/dominio/estructuras.h`) guarda de forma canónica el identificador, la *base* y el *tamaño* del mismo (cumpliendo con la premisa de almacenar "base y límite", siendo límite calculado estáticamente como base + tamaño).
- **Conexión Dinámica de Memory Sticks**: La lógica de handshakes fue refactorizada en *handlers* aislados (`conectar_memory_stick`). Al conectarse un módulo STICK, este reporta su tamaño, el cual se anexa inmediatamente a la `memoria_total` de la Memoria Principal. Se genera un `t_hueco_libre` nuevo que se añade a la lista global para permitir asignaciones de segmentos, y de forma transparente se ejecuta la función `fusionar_huecos_libres(ctx->huecos_libres)`.
- **Notificación asíncrona al Kernel**: Siguiendo el requerimiento de la consigna, la función `conectar_memory_stick` finaliza invocando a `notificar_memoria_expandida(ctx->scheduler_socket)`, avisándole al orquestador Scheduler que ya cuenta con un tamaño máximo ampliado de Memoria Total para comenzar o reactivar la admisión de procesos suspendidos.
- **Handlers Desacoplados**: El router de *handshakes* fue refactorizado para separar responsabilidades. En lugar de procesar los mensajes crudos dentro del `switch/if` principal, se implementaron *static voids* atómicos (`conectar_memory_stick`, `conectar_cpu`, `conectar_swap`) garantizando la legibilidad y mantenibilidad exigidas por la skill de refactorización del proyecto.

## Gestión de Fallos (BSOD y Desconexiones)

- **Desconexión Súbita de un Memory Stick (Corrupción)**: La consigna estipula explícitamente que la desconexión de un STICK debe corromper la memoria. Esto fue implementado de manera reactiva en el handler unificado de fin de socket `procesar_desconexion_cliente`. Al detectarse la terminación de una conexión (`recv` devuelve 0 o falla), el handler iterará sobre la lista de módulos STICK activos (`ctx->memory_sticks`). Si el descriptor del socket que acaba de caer (`cliente_fd`) coincide con el de un STICK, se activa inmediatamente la función de alerta `notificar_memoria_corrupta(ctx->scheduler_socket)`. Esto garantiza el envío de la señal de `CORRUPCION_MEMORIA` hacia el Scheduler para gatillar el flujo de finalización forzada por BSOD.

## Operaciones Estándar

- **Creación de Proceso**: La rutina para iniciar un proceso cumple estrictamente con el manual de operaciones. En el handler `procesar_crear_proceso_handler`, el `path` recibido se concatena con el path base del archivo de configuración (`ctx->base_path`) utilizando `string_from_format` para mayor legibilidad y seguridad. Luego, al invocar `crear_proceso`, se crea e inicializa el `t_contexto_ejecucion` y se blanquean todos los registros iterables en 0 mediante `memset(&(prog->contexto->registros), 0, sizeof(t_registros))`, un enfoque idiomático y eficiente en C, asegurando que el proceso inicie con un estado limpio, puro y neutro para la CPU.
- **Creación de Segmento (Algoritmos de Selección)**: La gestión de huecos libres para la creación de segmentos cumple cabalmente con la consigna. Al invocarse `buscar_hueco_libre_x_lista`, se evalúa la variable de configuración cargada en memoria (`ctx->allocation_strategy`). Mediante el uso seguro de `string_equals_ignore_case`, el Kernel Memory soporta la asignación dinámica bajo los esquemas obligatorios **"BEST"** (Best Fit: menor tamaño restante) y **"WORST"** (Worst Fit: mayor tamaño restante), e inclusive soporta **"FIRST"** Fit por consistencia. Para mantener los estándares de código limpio (regla DRY - Don't Repeat Yourself), se refactorizó la función `buscar_hueco_libre` eliminando código duplicado, y dejándola como un *wrapper* directo a `buscar_hueco_libre_x_lista`.
- **Compactación de Memoria**: Cuando la función `crear_segmento` detecta que hay espacio total suficiente pero fragmentado, señaliza la necesidad de compactación vía el flag `needs_compaction`. El handler `procesar_crear_segmento_handler` reacciona enviando un `SOLICITUD_COMPACTACION` al Kernel Scheduler, quien desaloja las CPUs antes de confirmar con `RESPUESTA_COMPACTACION`. Recién ahí, `compactar_memoria` reordena todos los segmentos al inicio del espacio de memoria, reubicando los datos físicamente entre Memory Sticks mediante `leer_memoria_distribuida`/`escribir_memoria_distribuida`, y actualizando las tablas de segmentos de todos los procesos vía `actualizar_tablas_segmentos`. El hueco resultante queda consolidado al final del espacio de direcciones. El `COMPACTION_DELAY` configurable simula la latencia del proceso.
- **Logs con PID Real (Corrección)**: Se detectó y corrigió un *placeholder* literal `<PID_FALTANTE>` en los logs de `crear_segmento` y `eliminar_segmento`. Para resolverlo limpiamente, se refactorizaron ambas firmas añadiendo el parámetro `uint32_t pid`, propagándolo desde los *handlers* que ya disponían de esta información. Esto garantiza que los logs cumplan con el formato de evaluación automática (`## PID: %d - Crear/Eliminar Segmento...`).
- **Corrección de Bug Lógico en `procesar_crear_segmento_handler`**: Se detectó que el `enviar_mensaje(MSG_OK)` estaba posicionado fuera del bloque `if (prog != NULL)` por un error de indentación. Esto causaba que se enviase una confirmación de éxito incluso cuando el programa no existía en memoria. Se corrigió reubicando la sentencia al nivel correcto.
- **Eliminación de Segmento**: El handler `procesar_eliminar_segmento_handler` recibe correctamente el PID y el ID de segmento como parámetros. El flujo se ejecuta en tres pasos atómicos: (1) se localiza y remueve la entrada correspondiente de la tabla de segmentos del proceso (`list_remove`), (2) se invoca `eliminar_segmento` que retira al segmento de la lista global (`ctx->segmentos_globales`), crea un nuevo `t_hueco_libre` equivalente y lo fusiona con adyacentes mediante `fusionar_huecos_libres`, y (3) se libera la memoria del segmento (`free`). Todo el bloque está protegido por `mutex_memoria` y `mutex_programas` para garantizar atomicidad ante accesos concurrentes.
- **Suspensión de Proceso (SWAP)**: La suspensión cumple fielmente con las tres restricciones de la consigna:
  1. *Movimiento de a 1 segmento*: La función `suspender_proceso` itera la tabla de segmentos y procesa cada uno individualmente — lee su contenido desde la memoria distribuida, lo escribe en SWAP bloque a bloque, y recién entonces libera el espacio en la memoria principal mediante `liberar_segmento_de_memoria`.
  2. *Aislamiento de bloques SWAP*: Los bloques se asignan por segmento a través de un bitmap (`t_bitarray*`). La función `buscar_bloques_libres_en_swap` garantiza que se encuentre un rango contiguo exclusivo para cada segmento, impidiendo que un bloque contenga datos de más de un segmento.
  3. *Verificación previa (Fail-Fast)*: Antes de iniciar la suspensión real, se ejecuta `hay_espacio_para_suspender_proceso`, que simula toda la asignación sobre una **copia** del bitmap (evitando mutación del estado real). Si la simulación falla, se aborta antes de tocar la memoria.
  4. *Refactorización DRY*: Se extrajo la lógica de búsqueda de bloques libres en SWAP (que estaba duplicada en `suspender_proceso` y `hay_espacio_para_suspender_proceso`) a la función estática `buscar_bloques_libres_en_swap`, eliminando ~30 líneas de código redundante.
- **Des-suspensión de Proceso**: El handler `procesar_desuspender_proceso` implementa un flujo robusto de restauración en tres fases: (1) *Verificación previa*: calcula la memoria total necesaria para todos los segmentos no triviales y verifica disponibilidad con `hay_espacio_para_restaurar_segmentos` (simulación sobre copia de huecos). Si no hay espacio contiguo pero sí total, solicita compactación al Scheduler. (2) *Restauración*: `restaurar_segmentos` utiliza el algoritmo de búsqueda de huecos configurado (`buscar_hueco_libre` → Best/Worst Fit) para asignar nuevas bases a cada segmento. Cada segmento se lee de SWAP bloque por bloque y se escribe en la memoria distribuida, limpiando los bits del bitmap de SWAP (`bitarray_clean_bit`). (3) *Regeneración de tabla*: la tabla global de segmentos se reconstruye creando nuevas entradas en `ctx->segmentos_globales` con las bases recién asignadas y `bloque_swap = -1` para desvincularlos del SWAP.
- **Finalización de Proceso (Corrección Crítica)**: Se detectó y corrigió un **memory leak severo** en `procesar_liberar_proceso_handler`. La implementación anterior solo liberaba los segmentos de la tabla pero no destruía: (1) el `t_programa` de la lista `ctx->programas`, (2) el array de instrucciones (`char** instrucciones` con cada string individual), (3) la estructura `t_contexto_ejecucion`, ni (4) la `t_list* tabla_segmentos`. La consigna exige explícitamente que se *"liberen todas las estructuras asociadas al proceso"*. La función fue reescrita con un flujo de 5 pasos secuenciales: eliminar segmentos de memoria → remover de `ctx->programas` → liberar instrucciones → liberar contexto → liberar programa. También se añadió un *guard clause* (Fail-Fast) al inicio en caso de PID inexistente.
- **Lectura y Escritura de Datos (Corrección Crítica de Protocolo)**: Se detectó un error grave de deserialización en `procesar_leer_memoria_handler` y `procesar_escribir_memoria_handler`. El Kernel Scheduler empaqueta las peticiones I/O utilizando `agregar_a_paquete`, el cual inyecta prefijos de tamaño (4 bytes) antes de cada variable. Sin embargo, Kernel Memory intentaba leer el stream crudo usando `buffer_read_uint32`, lo que causaba que interpretara el prefijo de tamaño como si fuese el valor real de la `dir_fisica`, corrompiendo por completo las operaciones. Ambos handlers fueron reescritos para utilizar `recibir_paquete`, el cual maneja correctamente el protocolo de tamaños dinámicos y devuelve una lista segura con los valores desempaquetados. Adicionalmente, tanto la lectura como la escritura soportan fragmentación entre múltiples *Memory Sticks* gracias al bucle de resolución de límites implementado en `escribir_memoria_distribuida` y `leer_memoria_distribuida`.
- **Cumplimiento de Logs Mínimos**: Se auditaron y estandarizaron todos los logs obligatorios de Kernel Memory según el formato estricto de la cátedra. Específicamente, se eliminaron los sufijos residuales en `Memory Stick Conectada` y `Proceso Creado` para que encajen byte a byte con el patrón de evaluación. Para el log de `Escritura / lectura en espacio de usuario`, se corrigió el protocolo `LEER_MEMORIA` y `ESCRIBIR_MEMORIA` emitido por el Kernel Scheduler (en llamadas a I/O como STDIN y STDOUT) forzando el envío del `PID` antes de la dirección y el tamaño. Esto habilitó a Kernel Memory a desempaquetarlo (`recibir_paquete`) y emitir exitosamente el log `## PID: <PID> - <Escritura/Lectura> - Dir. Física: <DIRECCIÓN_FÍSICA> - Tamaño: <TAMAÑO>` sin romper las interfaces existentes.
